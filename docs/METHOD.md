# HINT-SD WebShop: exact method and adaptation boundary

Public HINT-SD source is pinned at bc95b44192b06328a88773dbf3b345fa1c499093.
No upstream tracked file is patched. The original loss, tensor selection,
microbatch backward, optimizer/scheduler and EMA methods are executed directly.
This is a WebShop/Qwen2.5 environment adaptation, not an author-reported result.

## Original algorithm

Student online rollout -> skip successes -> EMA Teacher inspects the failed
trajectory -> select up to3 problematic steps and generate short local feedback
-> Teacher scores the SAME original sampled completion after an extra feedback
message -> Student matches Teacher only on those selected completions.

\[
\mathcal L=\frac{\sum_{i,t}m_{it}
D_{\mathrm{KL}}\!\left(\pi_\theta(\cdot\mid h_i,a_{i,<t})
\;\middle\|\;\operatorname{sg}\pi_{\bar\theta}(\cdot\mid h_i,f_i,a_{i,<t})\right)}
{\sum_{i,t}m_{it}},\qquad
\bar\theta\leftarrow0.999\bar\theta+0.001\theta.
\]

The actual public implementation selects the Student top100 vocabulary entries
plus a remaining-probability bucket. This is reverse KL, not a sampled-token
CE, a separate GRPO objective, RLSD advantage weighting or SDAR sigmoid gate.
No RETHINK, Route-SFT, external Analyzer/API, static skill or reference-KL term
is added. Hindsight is generated by the SAME EMA Teacher, not an external model.

The selected target is the full original assistant completion at that turn,
including think/action text, not just the text inside action tags. Other
turns, task/history observations and prefixes receive no selected-turn loss.
Original success skipping, max3 selection, parser and tensor masks are retained.
Unparseable or empty feedback produces no targets/inactive batches; no guessed
locations or GRPO fallback. Native no-op batches must not be reported as learning.

Student generation stores actual prompt and response token IDs. Teacher input
retains the exact visible, possibly left-truncated Student history, inserts
feedback at the chat boundary and scores the same completion IDs. No future
trajectory information is inserted into Student rollout or evaluation.

## Four-GPU transport without changing the objective

One training process/GPU holds Student and EMA LoRA adapters on a BF16 base.
Three other GPUs each hold one synchronous TP1 vLLM replica. Requests are
partitioned round-robin and restored to original order; fresh immutable LoRA
IDs publish current Student or EMA weights to every request. No old-policy
asynchronous rollout, fixed Teacher, quantization or multiplication of batch.

Native batch1 x accumulation2 x rollout4 means8 episodes per optimizer update,
not the128 episodes/update used by the GRPO/SDAR/RLSD comparison recipes.
Keep this difference visible when comparing150 updates; report episodes,
tokens and GPU time too. Four GPUs do not imply four gradient ranks.
Different inference batching/kernels are not bitwise equivalent to the author's
single-device colocation. The transport is a necessary resource adaptation.

Original LoRA q/v, rank32/alpha64/dropout.05, LR5e-6, linear schedule/5% warmup,
EMA.999, top100+tail and original distillation microbatch1 are retained.
The WebShop protocol uses prompt4096/response512/history2/max15 steps,
train/feedback temperature.6, eval temperature.4,150 optimizer updates,
initial/every5/final150 validation and save20/final150/latest2 checkpoints.
These benchmark/budget choices are explicit adaptations, not original BFCL
or AppWorld hyperparameter/results claims.

## Native environment and fixed task identity

The unmodified pinned SDAR WebShop worker, sparse terminal reward and parser
are used. The wrapper executes their exact AST bodies to avoid importing Ray
or a different training stack into the CPU service. The original native manager
formats observations, available actions, task extraction and history, including
its13000-character history fallback; the original SimpleMemory formats history.
No parser tightening, action retry or second prompt rendering is added.

Each actual game lives in an isolated CPU child, not a thread-shared native
catalog/RNG/Flask session. The loopback service only owns this job's children.
Tasks are content-ID checked on construction, reset, step and terminal auto-reset.
Mutating environment calls are not blindly retried after transport failures.

The assets, task_split.json and fixed_validation140.json are byte-identical to
the published GRPO, SDAR and RLSD WebShop baselines. Each of five native
categories contributes28 tasks;140 distinct target products. IDs ignore only
random generated price suffixes and ASIN aliases. All145 equivalent raw goal
entries are excluded from each training catalog BEFORE Actor interaction,
leaving6765 native entries/6719 unique families. Other native duplicates and
weights are not globally deduplicated. Training data rows retain all6765
entries of the seed0 filtered catalog. Original HINT-SD data sampling applies.

Validation uses the exact content IDs, seeds1000..1139 and local indices0..139
from the shared manifest. It is run in memory-bounded batches of4, not resampled.
Every task receives one Student-only rollout; no Teacher/hindsight at evaluation.
Initial observation identity, manifest/task split SHA, actual IDs and seeds
are recorded and checked across checkpoints/resume and model sizes.
Report success count/140, native sparse success and separate continuous task
score. This custom synthetic objective-held-out split is NOT canonical human500,
unseen-product or strict cross-domain zero-shot evaluation.

## Source, runtime and storage

Training uses the author's unmodified uv.lock/Python>=3.13 runtime. Native
WebShop runs in separate Python3.10/Java11/CPU-Torch2.8 environment so spaCy
and Lucene do not downgrade the original training dependencies. Public JSON
assets, NLP wheel and base weights are SHA/revision-pinned. No private files,
maintainer server or API key is required. Same-family1.5B and3B licenses differ.

Native checkpoint format retains Student/EMA adapters, optimizer, scheduler,
RNG and Trainer data progress. A storage-only wrapper calls the native serializer into same-filesystem staging,
checks CRC/SHA and atomically publishes before pruning older verified saves.
Partial/corrupt evidence stays untouched. Completion receipts hash all files; resume
requires matching model/data/source/recipe/code and a complete verified save.
Inference LoRA publications are temporary, not training checkpoints.
Native vLLM RNG and active CPU game sessions are not exact-replay checkpoints;
do not promise bitwise uninterrupted continuation.

CPU CI executes original KL, mask, native Trainer backward and EMA, checkpoint
restore, transport ordering, task identity/exclusion and real native
search/options/buy/reward, including a spawned CPU game. This does not establish
four-A100 CUDA memory fit, vLLM startup, actual GPU training or final scores.
No model scores are prefilled. A real GPU smoke is required before150 updates.
